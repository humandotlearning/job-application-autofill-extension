# Phoenix tracing implementation plan

**Goal:** Inspect the extension's exact AI requests and responses in local Phoenix.

**Architecture:** Use Phoenix's native JSON create-spans API from the extension service worker. Run the Python Phoenix server bound to loopback with a persistent, ignored local database. No relay or provider proxy.

**Constraints:** Preserve existing edits; never export HTTP authorization headers; failures in tracing must not break AI requests; no paid model call for verification.

1. Add `src/phoenix.js`: capture cloned response bodies, errors, model/token metadata and optional session IDs; send spans to `http://127.0.0.1:6006/v1/projects/job-autofill/spans` with a bounded timeout. Test with native Node Response objects and injected transport/settings.
2. Use the tracing fetch as the default for the five AI call types in `src/llm.js` and `src/learning-review.js`. Keep existing injected fetch behavior for tests. Correlate background planner and suggestions by application session.
3. Add a Settings checkbox and local dashboard link; document personal data persistence and best-effort delivery. Add a PowerShell launcher and pinned Python requirement.
4. Run focused tracing tests, existing tests, syntax checks and build. Start Phoenix, send synthetic data through the same tracing code, and read it back through Phoenix's API. Open the dashboard.
